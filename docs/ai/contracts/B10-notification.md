Verified against the code of branch `feature/b10-notification` (based on `main` at `7d2ad88`, which already contains B09). Order of authority: the code > this contract.

## 1. What B10 owns, and what it never does

- Table `notifications` (migration `V90__notifications.sql`, hand-applied, idempotent; Flyway is not active), entity `Notification` and the enums `NotificationType`, `NotificationChannel`, `NotificationStatus`, repositories `NotificationRepository` and `NotificationSourceRepository`, the package `service/notification/*`: `NotificationService`, `NotificationEventListener`, `NotificationQueryService`, `NotificationTemplateRenderer`, `EmailSender` (`SmtpEmailSender`, `LoggingEmailSender`), `EmailMessage`, `EmailSendException`; the configs `config/NotificationAsyncConfig` and `config/NotificationMailConfig`; the DTOs `MyNotificationResponse` / `AdminNotificationResponse` and the controllers `NotificationV1Controller` / `AdminNotificationV1Controller`.
- B10 only reads other modules' data, through projections in `NotificationSourceRepository` (it extends `Repository`, so it has no save/delete): the customer's `username`, `email` and `active` flag, the owner and total of an order, the owner and admin note of a return.
- B10 never writes the tables of B02–B09, never changes an event class or any code of another module (no change to `OrderService.transitionStatus`, `RefundService`, `ReturnService`, `AnalyticsEvent*`, `Permissions`, auth).
- A failure to notify never reaches the business flow (section 4).

## 2. Entity — `entity/Notification` (table `notifications`)

| Column | Type | Notes |
|---|---|---|
| `id` | `BIGSERIAL` PK | |
| `user_id` | `BIGINT` NOT NULL | `fk_notifications_user` → `users`, `ON DELETE CASCADE`; a plain id in the entity |
| `type` | `VARCHAR(50)` NOT NULL | a `NotificationType` name; `chk_notifications_type_format` checks only `^[A-Z][A-Z0-9_]*$` |

| `title` | `VARCHAR(255)` NOT NULL | the fixed subject of the type |
| `body` | `TEXT` NOT NULL | the PLAIN-TEXT message (shown in the app). The HTML email is rendered again from the same template and is not stored |
| `status` | `VARCHAR(20)` NOT NULL DEFAULT `'PENDING'` | `PENDING`, `SENT`, `FAILED` (`chk_notifications_status`) |

| `created_at` | `TIMESTAMP` NOT NULL | same zone |

Indexes: `idx_notifications_user_created (user_id, created_at DESC)` for the customer list, `idx_notifications_status_created (status, created_at)` for the admin filter. The entity declares the same columns, indexes and unique constraint, so `ddl-auto=update` and `V90` give the same table; the foreign key and the three CHECKs exist only after `V90` (guarded by `pg_constraint`). `NotificationMigrationDriftTest` keeps SQL, entity and enums aligned.

**Adjustments to the draft in `MODULE_SPECS.md` section 6 (with the reason):** `failure_reason` (the task needs a short reason on `FAILED` rows) and `dedupe_key` + `uq_notifications_dedupe` (the same event must never be sent twice) were added; `type` has a format CHECK instead of a closed list so a new type needs no DDL; listeners are `@TransactionalEventListener(AFTER_COMMIT)` instead of `@EventListener` (a rolled-back transaction must notify nobody; B09 convention).

## 3. Public Java signatures

```java
// service/notification/NotificationService  (none of these throws)

// service/notification/EmailSender
```

`send(...)` reads the customer by `userId` itself (the context only needs `orderId`, `orderTotal`, `returnId`, `refundRequired`, `note`; `customerName` is filled from the user). **Upgrade path (B13, message broker):** a consumer can call `send(userId, type, context)` or `deliver(...)` unchanged; the signature does not change, only who calls it.

## 4. Safety rules (the part other modules rely on)

- **Never fails the business flow.** Every listener runs `AFTER_COMMIT` with `fallbackExecution = false` (a rolled-back transaction notifies nobody; an event published outside any transaction is not notified) and is `@Async("notificationExecutor")`, so the lookups and the email never run on the request thread. `deliver` catches every `RuntimeException`; the log carries only the type, the user id and the exception class name, never the address, the content or an SMTP secret.
- **Its own transactions.** Reads use a read-only `REQUIRES_NEW` transaction and projections (nothing is lazy-loaded outside a session); every write is a `REQUIRES_NEW` transaction. The `TransactionTemplate`s are created inside the try block, so a commit failure cannot escape (same pattern as B09).
- **Executor.** `@EnableAsync` is switched on in ONE place, `NotificationAsyncConfig`. `notificationExecutor`: core 2, max 4, queue 200, thread prefix `notification-`, waits up to 10 s on shutdown. The rejection policy DISCARDS the task and logs one line; `CallerRunsPolicy` is deliberately not used (it would run the send on the request thread) and `AbortPolicy` is not used either (it would throw into the business flow). A dropped notification is not retried. Declaring an `Executor` bean makes Spring Boot skip its default `applicationTaskExecutor`; nothing in the repository uses that executor today (no other `@Async`, no MVC async), and `@Async` here always names `notificationExecutor`. A module that later needs `@Async` must name its own executor.
- **SMTP timeouts.** `mail.smtp.connectiontimeout=5000`, `timeout=10000`, `writetimeout=10000` so a hung server cannot pin an executor thread.

## 5. Notification types, templates and source events

All templates are Vietnamese; the subject is fixed per type; every dynamic value is HTML-escaped in the email and verbatim in the stored plain-text body; money is `125.000 ₫`. Only an order id, a return id, an order total, a refund flag and a staff note are used: no address, phone, token or payment data. Mapping convention = B09's `AnalyticsEventListener`.

| `NotificationType` | Subject | Source event (owner) | Condition | Dedupe key | Read by the listener |
|---|---|---|---|---|---|
| `ORDER_CREATED` | EcoGreen: Đặt hàng thành công | `OrderPlacedEvent(orderId, userId, total)` (B04) | always | `order:{id}:CREATED` | nothing (the event has `userId` and `total`) |
| `PAYMENT_SUCCESS` | EcoGreen: Thanh toán thành công | `OrderStatusChangedEvent` (B05) | `newStatus == PAID` | `order:{id}:PAID` | order owner + total |
| `ORDER_SHIPPED` | EcoGreen: Đơn hàng đang được giao | `OrderStatusChangedEvent` (B05) | `newStatus == SHIPPED` | `order:{id}:SHIPPED` | order owner + total |
| `ORDER_DELIVERED` | EcoGreen: Đơn hàng đã được giao | `OrderStatusChangedEvent` (B05) | `newStatus == DELIVERED` and `oldStatus != RETURN_REQUESTED` (that move means a return was rejected, not a new delivery) | `order:{id}:DELIVERED` | order owner + total |
| `ORDER_CANCELLED` | EcoGreen: Đơn hàng đã bị hủy | `OrderCancelledEvent(orderId, refundRequired)` (B05) | always | `order:{id}:CANCELLED` | order owner + total |
| `RETURN_CREATED` | EcoGreen: Đã ghi nhận yêu cầu đổi trả | `ReturnCreatedEvent(returnId, orderId, userId)` (B07) | always | `return:{id}:CREATED` | nothing |
| `RETURN_APPROVED` | EcoGreen: Yêu cầu đổi trả được chấp nhận | `ReturnStatusChangedEvent` (B07) | `newStatus == APPROVED` | `return:{id}:APPROVED` | return owner + order id + admin note |
| `RETURN_REJECTED` | EcoGreen: Yêu cầu đổi trả bị từ chối | `ReturnStatusChangedEvent` (B07) | `newStatus == REJECTED` (the admin note is included as the reason) | `return:{id}:REJECTED` | same |
| `RETURN_INFO_REQUESTED` | EcoGreen: Cần bổ sung thông tin đổi trả | `ReturnStatusChangedEvent` (B07) | `newStatus == INFO_REQUESTED` (the admin note is included) | `return:{id}:INFO_REQUESTED` | same |
| `RETURN_REFUNDED` | EcoGreen: Đã ghi nhận hoàn tiền đổi trả | `ReturnStatusChangedEvent` (B07) | `newStatus == REFUNDED` | `return:{id}:REFUNDED` | same |

Nothing is sent for any other order status (`PROCESSING`, `PACKED`, `RETURN_REQUESTED`, `RETURNED`, `REFUNDED`, `CANCELLED` via status change: the cancel email comes from `OrderCancelledEvent`) nor for the return statuses `PENDING` and `RETURNED`. The `RETURN_REFUNDED` wording says the refund is "recorded and being processed" on purpose: in B07 the status `REFUNDED` means a `PENDING` refund row was created, not that money has moved. There is no `PaymentSuccessEvent` (B06 is not changed): `PAYMENT_SUCCESS` is derived from `OrderStatusChangedEvent(newStatus = PAID)`; a COD order that goes `PENDING_PAYMENT → PROCESSING` gets no payment email.

**Failure codes (`failure_reason`), the only values ever stored:** `USER_DISABLED` (the account is inactive), `NO_EMAIL` (empty address, or one without `@`), `SEND_ERROR` (the mail server refused or failed), `EMAIL_NOT_CONFIGURED` (no `SMTP_HOST`). A notification for a user that does not exist writes no row (the foreign key would reject it) and is only logged.

## 6. De-duplication

`(user_id, type, dedupe_key)` is unique (`uq_notifications_dedupe`). `deliver` first checks `existsByUserIdAndTypeAndDedupeKey` (cheap, skips the work) and then relies on the constraint for races: a `DataIntegrityViolationException` on insert means "already handled" and nothing is sent. A `FAILED` row also counts, so a failed notification is not re-sent automatically (no retry). A `null` key (direct `send(userId, type, ctx)`) is never a duplicate, because PostgreSQL treats NULLs as distinct in a unique constraint.

## 7. Email transport and configuration

- `spring-boot-starter-mail` (version from the Boot BOM) provides `JavaMailSender`. `NotificationMailConfig.emailSender` returns `SmtpEmailSender` only when `spring.mail.host` has text AND a `JavaMailSender` exists, otherwise `LoggingEmailSender`. (`@ConditionalOnProperty` alone is not enough: an empty host counts as "present".)
- `SmtpEmailSender` sends the plain-text and the HTML version as one `multipart/alternative` UTF-8 message. **From address:** `SMTP_FROM`, else `SMTP_USERNAME` when it contains `@`, else the send fails with `EmailSendException("SMTP_NO_FROM_ADDRESS")` and the row is `FAILED` / `SEND_ERROR` (no invented address is ever used). `EmailSendException` carries a short code only and no cause, so no address or server detail reaches a log; `EmailMessage.toString()` prints only the user id and the type.
- `LoggingEmailSender` (development, tests, any environment without `SMTP_HOST`) delivers nothing and logs ONLY `type` and `userId`. **Status chosen for log-only mode: `FAILED` with `failure_reason = EMAIL_NOT_CONFIGURED`**, because nothing was delivered; `SENT` is reserved for a message the SMTP server accepted. This respects the `PENDING/SENT/FAILED` CHECK. The notification stays visible in the customer's list either way.
- Environment variables (all optional, none has a secret default; see `.env.example`): `SMTP_HOST`, `SMTP_PORT` (default 587), `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM` (no default, see the From rule above), `SMTP_AUTH` (default true), `SMTP_STARTTLS` (default true). They map to `spring.mail.*` and `ecogreen.notification.mail-from` in `application.properties` (additive).

## 8. Endpoints (`/api/v1`; envelope `{data, meta}`; errors `{error:{code,message}}`; size default 20, max 100)

| Method | Path | Auth | Request | Response | Errors |
|---|---|---|---|---|---|
| GET | `/api/v1/users/me/notifications` | logged-in user | `page?`, `size?`, `sort?` (`createdAt`, `id`; default `createdAt,desc`) | paged `[{id, type, channel, title, body, status, sentAt, createdAt}]`, only the caller's rows | 400 (bad sort), 401 |
| GET | `/api/v1/admin/notifications` | `analytics:view` | `status?` (`PENDING`/`SENT`/`FAILED`, case-insensitive), `page?`, `size?`, `sort?` (`createdAt`, `id`, `status`, `type`) | paged `[{id, userId, type, channel, title, status, failureReason, sentAt, createdAt}]` | 400 `VALIDATION_ERROR` (unknown status, bad sort), 401, 403 |

- The customer list takes the user id ONLY from the verified token; there is no user parameter and a `userId` in the query string is ignored. It never returns `failureReason` or `dedupeKey`.
- The admin list returns no body and no email address (so `analytics:view` does not expose customer content) and only the short failure code.
- Both lists are paged, use the two indexes above, and never call `findAll()` without a `Pageable`. Times are UTC instants (`ReportTime` from B09 is reused for the conversion; D-9 rule as in the B09 contract section 7).

## 9. TEMPORARY-COMPAT and known limitations

- **TEMPORARY-COMPAT: none** was created.
- **Only the EMAIL channel exists.** `User` has no phone, so SMS and PUSH are valid in the CHECK constraint but nothing sends them; no phone column was added.
- **No retry.** A `FAILED` row stays `FAILED`; a dropped task (executor saturated) is only logged. No scheduled re-send, no outbox.
- **No preferences or unsubscribe.** Every customer gets every notification of section 5; there is no opt-out and no per-type setting.
- **Best effort.** A notification is lost if the process dies between the commit and the listener, or while queued. If the final status update fails, the row stays `PENDING`.
- **`PENDING` rows** are possible only in that failure case (and briefly while sending); nothing sweeps them.
- The username is used as the greeting name (the user has no separate display name). The admin note of a return is included in the reject / info-request email: B07 already shows that note to the customer.
- The SQL of the unique constraint, the status update and the unique-violation path is exercised only by `NotificationPostgresTest`, which needs `ECOGREEN_TEST_PG_URL` and is skipped otherwise. A real SMTP delivery is not covered by any automatic test.
- `@Async` on a `@TransactionalEventListener` method (used so the lookups leave the request thread) is a supported Spring combination, but it has not been run against this application context by an automated test here.
