# B07 — Return & Refund contract

Owner: B07 (Return & Refund). Other modules append requests under "Requests for contract changes"; they do not edit this file or the code.
Verified against the code of branch `feature/b07-return-refund`. Order of authority: the code > this contract.

## 1. What B07 owns

- Tables `returns` (renamed from `return_requests`), `return_items`, `return_images`, and the column `refunds.return_id`. Migration `V60__returns_full.sql` (hand-applied, idempotent; Flyway is not active).
- The only place that restocks returned goods (`OrderInventoryPolicy` gives `RETURNED` / `REFUNDED` no inventory effect).
- Never writes `orders.status`: every order move goes through `OrderService.transitionStatus` (B05). `OrderStatusSingleWriterTest` stays valid.
- Reuses B06's `refunds` table; only adds the nullable `return_id`. Money is never sent by B07: staff complete the refund with `POST /api/v1/admin/payments/{orderId}/refund/complete` (B06).

## 2. Status enum — `entity/ReturnStatus`

`PENDING`, `INFO_REQUESTED`, `APPROVED`, `REJECTED`, `RETURNED`, `REFUNDED` (DB: `VARCHAR(30)` + `chk_returns_status`).

| From | Allowed next |
|---|---|
| `PENDING` | `INFO_REQUESTED`, `APPROVED`, `REJECTED` |
| `INFO_REQUESTED` | `APPROVED`, `REJECTED` |
| `APPROVED` | `RETURNED` |
| `RETURNED` | `REFUNDED` |
| `REJECTED`, `REFUNDED` | none (terminal) |

Open statuses (block a new return for the same order): `PENDING`, `INFO_REQUESTED`, `APPROVED`. `REJECTED` and `INFO_REQUESTED` require an admin note. Any other pair → 400 `BUSINESS_RULE_VIOLATION`.

## 3. Entities

`Return` (`@Entity(name = "ReturnRequest")` so existing JPQL keeps working; table `returns`): `id`, `order`, `user`, `reason` (100), `description` (2000), `imageUrl` (**deprecated**, legacy only), `status`, `adminNote`, `createdAt`, `updatedAt`.

`ReturnStatusHistory` (table `return_status_history`, append-only): `return`, `oldStatus` (null on the first row), `newStatus`, `changedBy`, `note`, `changedAt`. One row on create and one per status change; `adminNote` keeps only the latest note, the history keeps all of them.
`ReturnItem`: `id`, `returnRequest`, `orderItem`, `quantity` (> 0; unique per `(return_id, order_item_id)`).
`ReturnImage`: `id`, `returnRequest`, `imageUrl` (server-generated file URL), `sortOrder`.
`Refund` gains `returnId` (nullable). Legacy returns (no items) are whole-order records: they can be approved or rejected only; `RETURNED` / `REFUNDED` are refused for them and `allowedNextStatuses` hides those two.

## 5. Endpoints (`/api/v1`)

| Method | Path | Permission | Notes |
|---|---|---|---|
| POST | `/returns` | any authenticated user | `multipart/form-data`: `orderId`, `reason` (≤ 100), `description?` (≤ 2000), `items` (JSON `[{"orderItemId":N,"quantity":N}]`, ≥ 1), `images` (1–5 files, JPG/PNG/WebP checked by content, ≤ 5 MB each). Owner comes from the token. 201 + `{data: ReturnDto}` |
| GET | `/returns/my` | any authenticated user | paged (`page`, `size`, `sort=createdAt,asc\|desc`) |
| GET | `/returns/{id}` | owner, or `return:view` | 403 for another customer |
| GET | `/admin/returns` | `return:view` | paged; optional `status` (unknown value → 400 `VALIDATION_ERROR`) |
| PATCH | `/admin/returns/{id}/status` | `return:process` | `{ newStatus, adminNote? }` → `ReturnDto` |

`ReturnDto`: `id, orderId, userId, username, status, reason, description, adminNote, items[{orderItemId, productId, productName, quantity, unitPrice}], images[url], refund{status, amount}|null, refundMessage|null, createdAt, updatedAt, allowedNextStatuses[], history[{oldStatus, newStatus, changedBy, note, changedAt}]` (empty unless the caller may process returns). `history` is filled by `GET /returns/{id}` and the status change response, empty in lists.

Errors: 400 `VALIDATION_ERROR` (malformed items JSON, bad status), 400 `BUSINESS_RULE_VIOLATION` (order not `DELIVERED`, open return exists, quantity above ordered, invalid transition, missing note), 401, 403, 404.

## 6. Side effects per transition (all in one transaction)

- **create:** order locked; order must be `DELIVERED`, owned by the caller, no open return; items validated against the order; files stored; order → `RETURN_REQUESTED` via `transitionStatus`. On failure the stored files are deleted.
- **→ REJECTED:** order → `DELIVERED` via `transitionStatus` (legacy returns without items leave the order untouched).
- **→ RETURNED:** order → `RETURNED` via `transitionStatus`, then `InventoryGateway.restock(productId, qty, "RETURN", returnId)` once per product, in ascending `productId` order (B03 lock rule; quantities of the same product summed; idempotent by B03's key).
- **→ REFUNDED:** locks the payment; if it is `SUCCESS` and no live refund exists, creates a `PENDING` `Refund` (`reason = "RETURN"`, `return_id`, `created_by` = actor). Amount: the item prices × quantities for a partial return, the exact payment amount when every unit is returned; capped at the payment amount. A payment that is not `SUCCESS` (for example COD not yet collected) creates no refund row and the DTO carries `refundMessage`. Order → `REFUNDED` via `transitionStatus`.
- Staff then complete the money transfer with B06's `refund/complete` endpoint.

## 7. TEMPORARY-COMPAT

- `Return.imageUrl` / `returns.image_url` — deprecated, nullable; legacy rows are back-filled into `return_images`. Remove the column in a later release once no reader remains (do not drop in the same release).

## 8. Known limitations and open decisions

- `PAID` orders cannot be returned (D-4): the order state machine has no `PAID → RETURN_REQUESTED`; the UI offers the action only for `DELIVERED`.
- Multipart request limit is 6 MB (existing property, unchanged), so five large images cannot all be uploaded; the UI limits the total to about 5.5 MB.
- A wrong `Content-Type` or a missing multipart part may surface as a generic 500 because `GlobalExceptionHandler` (B01) has no handler for those exceptions.
- The refund amount rule and the COD handling above are B07's decision and open for the owner's confirmation.
- Backend tests were written but could not be run where this was built (Maven Central unreachable); V60 was run against a throw-away PostgreSQL only.
