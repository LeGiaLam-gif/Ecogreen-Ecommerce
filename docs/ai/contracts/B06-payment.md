# B06 — Payment contract

Owner: B06 (Payment). Other modules append requests under "Requests for contract changes"; they do not edit this file or the code.
Verified against the code of branch `feature/b06-payment`. Order of authority: the code > this contract.

## 1. What B06 owns

- Tables `payments` (extended) and `refunds` (created here; B07 reuses it and must not create it again). Migrations `V50`, `V51`.
- The payment provider abstraction, the public webhook, manual confirmation of VietQR / MoMo transfers, refund records.
- Never changes `orders.status` itself: the only writer is `OrderService.transitionStatus` (B05).

## 2. Status enums (for B07 and the frontend)

| Enum | Values | Meaning |
|---|---|---|
| `Payment.Status` | `PENDING`, `SUCCESS`, `FAILED`, `CANCELLED`, `REFUNDED` | `PENDING` created with the order / waiting for the provider or for staff; `SUCCESS` money received; `FAILED` the provider reported a failure; `REFUNDED` a refund was completed. `CANCELLED` is reserved (no B06 code writes it yet) |
| `Refund.Status` | `PENDING`, `SUCCESS`, `FAILED` | `PENDING` created when a paid order is cancelled; `SUCCESS` staff sent the money |
| Payment method | `COD`, `VIETQR`, `MOMO`, `VNPAY` | one list: `PaymentService.SUPPORTED_METHODS`; DB column is free `VARCHAR(50)` validated in the service |
| Provider (`payments.provider`) | `VNPAY`, `MOCK`, null | null when no gateway is involved (COD, manual confirmation) |

Method rules: `VNPAY` is paid through a gateway; `COD` has no payment step; `VIETQR` and `MOMO` are static QR codes with no confirmation signal and are confirmed by staff (`payment:confirm`).

## 3. Entities

`Payment`: `id`, `order` (many-to-one; one payment per order), `paymentMethod`, `amount` (`DECIMAL(12,2)` VND), `status`, `transactionId` (merchant reference of the **current** gateway attempt), `provider`, `paidAt`, `rawResponse` (**write-only**: never returned by the API, never logged), `createdAt`, `updatedAt`.

`Refund`: `id`, `payment`, `order`, `amount` (the full payment amount), `status`, `reason`, `providerTransactionId`, `createdBy` (null for the system), `createdAt`, `refundedAt`. At most one non-`FAILED` refund per order (partial unique index).

## 4. Public Java signatures

```java
// service/PaymentService
static String requireSupportedMethod(String method);                        // BadRequestException when unknown (includes VNPAY)
Payment createPendingPayment(Order order, String method);                   // B04 contract, unchanged
Payment getByOrderId(Long orderId);                                          // 404 when absent
Payment getPaymentFor(Long orderId, Long userId, boolean canViewAny);       // owner, or canViewAny; else ForbiddenException
PaymentInitiationResult initiatePayment(Long orderId, Long userId, String returnUrl, String clientIp);
WebhookOutcome handleWebhook(String provider, Map<String,String> params);   // PROCESSED | ALREADY_PROCESSED | INVALID_SIGNATURE | PAYMENT_NOT_FOUND | AMOUNT_MISMATCH
Payment confirmManually(Long orderId, Long actorUserId, String note);       // VIETQR / MOMO, PENDING only
Payment updateMethod(Long orderId, Long userId, String method);
WebhookOutcome mockPay(Long orderId, Long userId, boolean success);         // TEMPORARY-COMPAT(B06)
List<AdminPaymentSummaryResponse> listSummaries(Collection<Long> orderIds);

// service/RefundService
boolean createPendingRefundIfAbsent(Long orderId);                           // REQUIRES_NEW; full amount; no-op if a non-FAILED refund exists
Refund completeRefund(Long orderId, Long actorUserId, String providerTransactionId); // refund SUCCESS, payment REFUNDED

// service/payment/PaymentGatewayClient (one bean per provider; JDK HMAC only, no extra library)
String providerCode();
boolean isAvailable();                                                       // default true; false when not configured
PaymentInitiationResult initiate(Payment payment, String returnUrl, String clientIp);   // result: redirectUrl + a NEW transactionRef
WebhookVerificationResult verifyAndParse(Map<String,String> params);        // never touches the database
```

`handleWebhook` order of steps (part of the contract): (1) verify the signature — invalid: reject, nothing read or written; (2) load the payment by `(provider, reference)` with a pessimistic row lock; (3) status other than `PENDING`: already processed, `transitionStatus` is never called twice; (4) the amount must equal `payment.amount`, else reject; (5) success: `SUCCESS`, `paid_at`, `raw_response`, then `transitionStatus(orderId, PAID, null, "Auto by payment webhook")`; (6) failure: `FAILED`, then `transitionStatus(orderId, CANCELLED, null, "Payment failed")`. If the transition throws, the whole transaction rolls back and the caller answers a retryable code.

Events: B06 publishes none. It consumes `OrderCancelledEvent(orderId, refundRequired)` (B05) with `@TransactionalEventListener(AFTER_COMMIT)` (`RefundOnCancelListener`): when `refundRequired` is true it creates ONE `PENDING` refund for the full payment amount in a new transaction. A failure there is logged and never fails the cancellation (the history note `REFUND_REQUIRED` remains).

## 5. Endpoints (`/api/v1`, envelope `{data, meta}`, errors `{error:{code,message,fields?}}`)

| Method | Path | Permission | Request | Response / errors |
|---|---|---|---|---|
| POST | `/payments/{orderId}/initiate` | owner | optional `{returnUrl ≤ 500}` | `{redirectUrl, provider}`. 401, 403 (not owner), 404, 400 `BUSINESS_RULE_VIOLATION` (order not `PENDING_PAYMENT`, already paid, method without gateway, VNPAY not configured and mock disabled) |
| GET | `/payments/{orderId}` | owner or `payment:view` | — | `PaymentResponse`. 401, 403, 404 |
| PUT | `/payments/{orderId}/method` | owner | `{method}` | `PaymentResponse`. 400 `VALIDATION_ERROR` (blank / unknown), 400 `BUSINESS_RULE_VIOLATION` (order not waiting for payment, already paid), 403, 404 |
| POST | `/payments/{orderId}/mock-pay` | owner | `{outcome: SUCCESS\|FAILED}` | `PaymentResponse`. **TEMPORARY-COMPAT(B06)**; 400 unless mock is enabled and the attempt used the mock provider |
| GET, POST | `/payments/webhook/{provider}` | **public** | provider parameters (VNPay: query string) | see 5.1 |
| GET | `/admin/payments?orderIds=…` | `payment:view` | up to 100 ids | `[AdminPaymentSummary]`. 400 when more than 100 |
| POST | `/admin/payments/{orderId}/confirm` | `payment:confirm` | optional `{note ≤ 500}` | `PaymentResponse`. 400 `BUSINESS_RULE_VIOLATION` (COD or gateway method, not `PENDING`, order not payable), 404 |
| POST | `/admin/payments/{orderId}/refund/complete` | `payment:refund` | optional `{providerTransactionId ≤ 100}` | `Refund` `{id, orderId, amount, status, reason, providerTransactionId, createdAt, refundedAt}`. 404 when the order has no `PENDING` refund |

`PaymentResponse`: `id, orderId, paymentMethod, amount, status, transactionId, provider, paidAt, mockEnabled`. It never contains `raw_response`.
`AdminPaymentSummary`: `orderId, paymentMethod, paymentStatus, amount, refundStatus` (null without a refund). Orders without a payment are omitted.

Permissions `payment:view`, `payment:confirm`, `payment:refund` already existed (`V6`); B06 adds none.

### 5.1 The webhook — the one response that is not the envelope

`GET|POST /api/v1/payments/webhook/{provider}` has no `AuthGuard`; the provider's signature is the only protection (HMAC-SHA512 for VNPay). It answers the gateway in the gateway's own JSON with HTTP 200:

| `RspCode` | `Message` | When |
|---|---|---|
| `00` | Confirm Success | recorded |
| `02` | Order already confirmed | repeated delivery, nothing changed |
| `01` | Order not found | no payment has this reference |
| `04` | Invalid amount | amount differs from the payment |
| `97` | Invalid signature | signature missing or wrong |
| `99` | Unknown error | could not be recorded (rolled back, includes provider not configured): deliver again |

An unknown provider code is the standard `404` envelope. Besides B02 file downloads this is the only non-envelope response.

## 6. Provider rules

- **VNPAY** (API 2.1.0): `vnp_Amount` = amount × 100 as an integer; HMAC-SHA512 over the key-sorted, URL-encoded `k=v&k=v` string of all `vnp_*` parameters except `vnp_SecureHash` / `vnp_SecureHashType`; constant-time comparison; success only when `vnp_ResponseCode = "00"` **and** `vnp_TransactionStatus = "00"`; `vnp_TxnRef` is unique per attempt (`<orderId>-<yyyyMMddHHmmss>-<8 hex>`); dates in `Asia/Ho_Chi_Minh`; `vnp_OrderInfo` is ASCII. Empty tmn-code or secret: **fails closed** (`BusinessRuleViolationException`), the application still starts.
- **MOCK**: a bean only when `ecogreen.payment.mock-enabled=true`. It is used for `VNPAY` payments only when VNPay is not configured. Its callbacks are signed with a key generated at start-up and known only to the process, and they go through the same `handleWebhook`.
- `returnUrl` from the client is used only when it starts with `ecogreen.payment.return-url` (followed by end, `?`, `#` or `/`); otherwise the configured URL is used. `orderId` is appended as a query parameter.

## 10. Known limitations

- **No automatic gateway refund.** A refund is a `PENDING` record; staff send the money outside the system and complete it with the endpoint above.
- **No payment expiry / abandoned-order job.** An unpaid `PENDING_PAYMENT` order keeps its reserved stock until it is cancelled by hand or by its owner.
- **The IPN needs a public URL.** VNPay can only call the webhook when the backend is reachable from the internet (for example through ngrok); locally use the mock provider.
- **One payment row per order, one live reference.** A new `initiate` replaces the reference of the previous attempt. A late successful callback for the replaced reference is answered `01` and not recorded; staff must reconcile it by hand.
- A successful callback for an order that was cancelled meanwhile cannot move the order to `PAID`: the transaction rolls back, the callback is answered `99` and repeats until the provider gives up. The money must be reconciled by hand.
- The client IP sent to VNPay is `request.getRemoteAddr()` (`X-Forwarded-For` is not trusted); IPv6 addresses are replaced by `127.0.0.1`.
- The staff user who completes a refund is only logged, not stored (`refunds.created_by` is the creator, null for the system).

## 11. Open decisions

- **Failed payment cancels the order** (draft default, implemented): `FAILED` payment → `transitionStatus(CANCELLED, null, "Payment failed")`, which releases the stock. Alternative: keep the order `PENDING_PAYMENT`, set the payment `FAILED` and let the customer retry (`initiate` already accepts a `FAILED` payment on a `PENDING_PAYMENT` order). Needs an owner decision.
