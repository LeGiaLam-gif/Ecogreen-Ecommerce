## 4. Recording rules (the part other modules rely on)

- `track` ignores (logs, no payload) an event type that is not in `AnalyticsEventTypes.ALL`; it never throws. The write runs in a `TransactionTemplate` with `REQUIRES_NEW` created **inside** the try block, so a failing insert or commit can neither fail nor roll back the caller's transaction (a `@Transactional` method would let a commit failure escape its own catch).
- The payload is sanitised before storage: keys must match `[A-Za-z][A-Za-z0-9_]{0,39}` and must not contain `email, mail, token, password, passwd, secret, address, phone, card, cvv, authorization, cookie, signature, bank` (case-insensitive); values must be String (cut to 200), Boolean, Number or Enum; nulls and nested values are dropped; at most 20 keys; `session_id` is cut to 100. **Never put personal data, credentials or raw payment data in a payload.**
- Every listener is `@TransactionalEventListener(phase = AFTER_COMMIT)` with `fallbackExecution = false` (guarded by `AnalyticsEventListenerTest.listener_runsAfterCommit_only`): a rolled-back transaction records nothing, and an event published **outside** any transaction is not recorded.

## 5. Events: what is recorded, owner, publish point

| `event_type` | Source event (owner) | Published at | Mapping / payload | `user_id` |
|---|---|---|---|---|
| `order_created` | `OrderPlacedEvent(orderId, userId, total)` (B04) | last step of `CheckoutService.checkout`, same transaction | `{orderId, total}` | event `userId` |
| `payment_success` | `OrderStatusChangedEvent(orderId, oldStatus, newStatus, actorUserId)` (B05) | `OrderService.transitionStatus` | only when `newStatus == PAID`: `{orderId, previousStatus, orderTotal}`. There is no `PaymentSuccessEvent` (B06 is not changed); a COD order moving `PENDING_PAYMENT → PROCESSING` is **not** a `payment_success` | order owner (read after commit) |
| `order_cancelled` | `OrderCancelledEvent(orderId, refundRequired)` (B05) | `OrderService.transitionStatus` when the new status is `CANCELLED` | `{orderId, refundRequired, orderTotal}`; the spec's `reason` does not exist in the event | order owner (read after commit) |
| `return_created` | `ReturnCreatedEvent(returnId, orderId, userId)` (B07) | `ReturnService.create` | `{returnId, orderId}` | event `userId` |
| `return_status_changed` | `ReturnStatusChangedEvent(returnId, orderId, oldStatus, newStatus)` (B07) | `ReturnService.updateStatus` | `{returnId, orderId, oldStatus, newStatus}` | null |

Any other `OrderStatusChangedEvent` records nothing.

**Not recorded (nobody publishes them):** `product_view` (B02), `add_to_cart` and `checkout_started` (B04); and `PaymentSuccessEvent` (B06). B09 did not create these event classes or whitelist their types, because a class nobody publishes is a contract nobody agreed to. See section 9.

## 6. Endpoints (all `analytics:view`; `/api/v1`; envelope `{data, meta}`; errors `{error:{code,message}}`)

| Method | Path | Request | Response | Errors |
|---|---|---|---|---|
| GET | `/api/v1/admin/analytics/events` | `type?`, `from?`, `to?`, `page?`, `size?` (default 20, max 100), `sort?` (`createdAt`, `id`, `eventType`; default `createdAt,desc`) | paged `[{id, eventType, userId, sessionId, payload, createdAt}]` | 400 `VALIDATION_ERROR` (unknown `type`, unparsable or offset-less `from`/`to`, `from` after `to`, window > 366 days, bad `sort`), 401, 403 |
| GET | `/api/v1/admin/reports/low-stock` | `threshold?` (default 10, 0..1,000,000), `page?`, `size?` | paged `[{productId, productName, sku, available}]`, lowest available first | 400 (threshold), 401, 403 |
| GET | `/api/v1/admin/reports/pending-orders-count` | — | `{status: "PENDING_PAYMENT", count}` | 401, 403 |
| GET | `/api/v1/admin/reports/refund-summary` | `from?`, `to?` (`yyyy-MM-dd`) | `{from, to, currency: "VND", items: [{status, count, totalAmount}], totalAmount}` | 400 (bad date, `from` after `to`, window > 366 days), 401, 403 |
| GET | `/api/v1/admin/reports/customer-frequency` | `page?`, `size?` | paged `[{userId, orderCount, totalSpent, firstOrderAt, lastOrderAt}]` | 401, 403 |

Definitions:

- **Pending** = `OrderStatus.PENDING_PAYMENT` (placed, awaiting payment). `PAID` orders waiting to be processed are **not** pending.
- **Low stock** = `available = quantity_on_hand − reserved_quantity ≤ threshold` in the B03 `inventory` table (via `InventoryAdminService.list`). `products.stock_quantity` is frozen and never read. The response shows `available` only (the B03 contract keeps on-hand and reserved in `/api/v1/admin/inventory`).
- **Refund summary**: refunds with status `PENDING` or `SUCCESS`, selected by `refunds.created_at` on the calendar days `from`..`to` inclusive; amounts are `BigDecimal` `DECIMAL(12,2)` in VND; `items` always has both statuses (zero-filled); `FAILED` is excluded; `totalAmount` = sum of the items. Statuses are passed as `Refund.Status` parameters.
- **Customer frequency**: orders per `user_id` whose status is in `OrderStatus.revenueStatuses()` (passed as a parameter, never a literal), one grouped query plus one count query regardless of the number of customers (no N+1). Fixed order: most orders, then user id. It exposes no name or email, so `analytics:view` alone shows no personal data.
- The legacy revenue reports (`/api/admin/reports/*`, `StatsController`) are untouched (still `requireAdmin`, bare JSON); the new endpoints live in `AdminReportV1Controller` / `AdminAnalyticsV1Controller` to keep the two API generations apart.

## 7. Time zone (open decision D-9)

`timestamp` columns hold **local** time of the JVM / database session zone (today `Asia/Ho_Chi_Minh`: `BackendApplication` sets the JVM default and the datasource URL sets `timezone`). The API speaks UTC ISO-8601:

- `from` / `to` of the events list must carry an offset; they are converted to the local zone before they reach the query. The window is `[from, to)`.
- `createdAt`, `firstOrderAt`, `lastOrderAt` are returned as UTC instants.
- Refund-summary `from` / `to` are calendar days in the **local** zone (`from` 00:00 inclusive to the next midnight after `to`).
- `ReportTime.zone()` is the JVM default zone, so the code stays right if D-9 is resolved by changing the zone in both places. It is **wrong if the JVM zone and the database session zone differ**.

## 8. TEMPORARY-COMPAT and known limitations

- **TEMPORARY-COMPAT: none** was created.
- Payload is flat JSON only (`AnalyticsPayloadJson`, no JSON library, in the style of `ReturnItemsJson`); a payload with nested values loses those values.
- The events list without `type` cannot use `idx_analytics_events_type_created` for the time range (the index starts with `event_type`); the 366-day cap and the default 30-day window bound the scan. Add an index on `created_at` only if a measured need appears.
- The refund summary and customer frequency have no supporting index on `refunds.created_at` / `orders(status, user_id)`; `orders` already has `(status, created_at DESC)`. The 366-day cap bounds the refund scan. Not measured.
- Events are not recorded when the publisher runs outside a transaction (`fallbackExecution = false`) or when the process dies between commit and the listener; analytics are best-effort, not an audit trail.
- There is no de-duplication: if a publisher ever publishes the same event twice, it is recorded twice.
- The SQL of the aggregations and the jsonb round trip are only exercised by `AnalyticsPostgresTest`, which needs `ECOGREEN_TEST_PG_URL` and is skipped otherwise.
